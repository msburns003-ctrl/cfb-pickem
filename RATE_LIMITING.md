## Summary

Added `express-rate-limit` to the CFB Pick'em API to protect auth, pick
submission, admin, and read endpoints from abuse, brute-force attempts, and
runaway clients. Tuned for a ~40-member private league.

**No user-facing behavior changes are expected under normal traffic.** All
thresholds sit well above real usage patterns.

## Configuration

All limits live in `server/rateLimit.ts`. Each limiter is commented in-file
with its rationale, routes it covers, and tuning notes.

| Limiter | Window | Max | Key | Routes |
|---|---|---|---|---|
| `authLimiter` | 15 min | 5 | IP | `POST /api/auth/login`, `POST /api/auth/change-password` |
| `pickWriteLimiter` | 1 min | 40 | user id → IP | `POST /api/weeks/:id/picks`, `.../picks/batch`, `.../upset-pick`, `POST /api/cristoball/me` |
| `readLimiter` | 1 min | 120 | user id → IP | `GET /api/auth/me`, `/weeks`, `/weeks/:id/dashboard`, `/weeks/:id/grid`, `/standings`, `/cristoball/me` |
| `adminLimiter` | 1 min | 60 | user id → IP | `/api/admin/*` (all 15+ admin routes) |
| `globalLimiter` | 1 min | **600** (rollout) → 300 (target) | IP | `/api/*` fallback; admins skipped |

### Why these numbers (for a 40-member league)

- **Auth 5/15min:** OWASP guidance for credential-stuffing / brute-force
  protection. `skipSuccessfulRequests: true` means a valid login after a
  typo does not count against the user.
- **Pick 40/min:** A user editing all ~12–15 weekly games in quick
  succession generates a burst. 40/min leaves headroom for corrections
  without allowing a runaway script.
- **Read 120/min:** Game-day refresh behavior can be aggressive.
  2 refreshes/sec/user is fine; bots at 10/sec are not.
- **Admin 60/min:** Bursty admin work (week lock + bulk member updates)
  fits comfortably.
- **Global 600/min (rollout) → 300 (target):** Conservative for week 1 to
  avoid false-positives, then tightened after log review.

## Deploy-Time Changes

### Trust proxy — CRITICAL

Added to `server/index.ts`:

```ts
app.set("trust proxy", 1);
```

The `*.pplx.app` hosting proxy sits in front of the server. Without this,
every request would appear to come from the proxy's IP and all users would
share one bucket — instantly locking everyone out.

### Store

Uses the default in-memory store from `express-rate-limit`. This works
correctly here because the server is long-lived (`httpServer.listen(...)`
on a PORT env var) — **not** serverless. No Redis / Upstash required.

If the app is ever migrated to Vercel serverless functions, this must be
swapped for a shared Redis store (see commented note in `rateLimit.ts`).

## Logging

Every 429 is logged via `console.warn` in a structured, greppable format:

```
[rate-limit] 429 limiter=<name> route=<METHOD> <path> user=<id|anon> ip=<ip> max=<n> windowMs=<ms>
```

Fields:
- `limiter` — which of the five buckets triggered
- `route` — full method + path
- `user` — authenticated user id, or `anon` if unauthenticated
- `ip` — client IP (populated correctly thanks to `trust proxy`)
- `max` / `windowMs` — the limiter's config at time of rejection

**Review cadence:** During the first 7 days, grep the server logs daily for
`[rate-limit] 429`. If any legitimate league member's user id shows up,
loosen the specific limiter that caught them.
